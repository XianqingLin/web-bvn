# BVN Web —— 联机设计稿

> 本文档定联机的**产品形态与协议设计**（房间/匹配/选人同步/地图抽取/异常流）；引擎侧"必须怎么做"仍以 [ARCHITECTURE.md](ARCHITECTURE.md) 为准，core 侧联机设计见 [DESIGN.md](DESIGN.md) §6。
> 需求定案日：2026-11-16（与用户逐条确认）；决策变更就地修改对应段并写明日期。
> 背景：本游戏将嵌入"GameDock"平台（类 Steam 容器）运行，平台提供账号、好友与邀请。

---

## 1. 定位与边界

- **联机是游戏自己的事**：房间管理、匹配队列、数据中转全部归游戏自有联机服务器（`server/room-server.mjs` 定位）。平台不做联机（无大厅/房间/匹配/中转），2026-11-16 方案 A（平台唯一权威 + 通用字节管道）已作废。
- **平台只提供两样**：
  - **好友邀请（仅信息传递）**：邀请发出与展示、点击后带连接参数进入游戏页——对应 Steam 的 Rich Presence `+connect` 深链；
  - **身份凭证**：可验证"当前操作者 = 平台用户 X"——对应 Steam 的 `GetAuthSessionTicket`。
- 设计基准场景：**1v1 联机对局**（lockstep，既有 `packages/net` + `server/room-server.mjs` 语义为地基），房间/匹配/选人流程全部架在其上。

## 2. 身份与账号（游戏侧零账号逻辑）

| Steam 侧机制 | 本项目对应 |
|---|---|
| SteamID 当账号（游戏不建号） | **平台用户 ID 当账号**：服务器验证平台凭证后，以用户 ID 为主键查/建玩家档案 |
| GetAuthSessionTicket / BeginAuthSession | 平台身份凭证 + 服务器侧验证接口（对齐点见 §11） |
| persona name | 平台昵称：房间内、VS 横幅、对局 HUD 显示名一律取平台资料 |
| 好友关系归 Steam | 好友关系归平台，游戏不感知 |

对局内显示不使用"游戏内起名"之类的第二身份——只有一个身份（平台账号），降低约定成本。

## 3. 主菜单入口与场景流

主菜单新增联机区，**3 个按钮**：

| 按钮 | 行为 |
|---|---|
| **创建房间** | 进房间页（房主位），等待玩家加入（好友邀请 / 房码） |
| **浏览房间** | 公开房间列表 → 选房加入（客座位） |
| **随机匹配** | 进服务器匹配队列，成功后直接进对局流程 |

场景链（新增部分粗体）：

```
Menu → **Room（建房/浏览加入/邀请进入）** → SelectFighter（联机双光标）→ MapSelect（房主选/开箱抽取）→ 对局（既有 lockstep）
Menu → **Matchmaking（匹配中）** → VS 横幅 → SelectFighter → …
```

对局前置数据在进对局前全部敲定（角色/援助/地图/种子），`configHash` 互验机制不变——对局阶段协议零改动。

## 4. 房间页

- **房主**：无准备按钮（视为常备）；有**开始按钮**，仅在客座已准备时可点；点击后双方进选人页。
- **客座**：**一个准备/取消准备切换按钮**（非两个按钮）。
- **房主设置项**（客座只读可见，变更实时广播）：
  - **公开/私人**：公开房间进 §5 浏览列表；私人只能房码或邀请进入；
  - **随机地图**勾选：决定 §8 走房主选择还是开箱抽取；
  - **团队模式**开关：开 = 每人选 3 名角色 + 1 名援助；关 = 单挑 1v1。
- 页面显示：房间码、双方昵称与准备状态、各项设置。
- 提供"邀请好友"操作：调平台邀请接口，携带房间码（平台负责展示与深链）。
- 离开房间 → 回主菜单；房主离开即房间解散（既有语义：断开即离开）。

## 5. 浏览房间

- 列表内容：公开房间——房主昵称、团队模式标记、可加入/已满状态。
- 点击加入：满员/已开局/房主刚解散 → 明确的错误提示（room-full / room-not-found 等既有错误码复用）。
- 列表刷新：进入页面拉取 + 定时轮询（服务器不做主动推送，量级不需要）。
- 不做房间名/密码——私人房的隐私靠"不出现在列表"达成。

## 6. 随机匹配

- 点击"随机匹配"后按钮文字变"**匹配中**"；**取消 = 按钮右侧滑出红色 ✕ 按钮**（紧挨，方案一定案）——一次点击、零二级交互。子菜单方案仅在将来出现多个匹配操作（偏好设置等）时再考虑。
- **匹配默认设置**：团队模式**开启**、地图**强制随机**（不走房主选择）。这两个是匹配的固定属性，不提供选项。
- 匹配成功 → **VS 横幅**：屏幕中央，左右双方头像 + 昵称，中间"VS"，配"已找到对手"文案。
  - 展示时长：**下限约 2.5 秒，上限以建连就绪为准**——横幅持续显示到双方连接就绪才切入选人页（后台在横幅期间完成建房/入房/对时），不是死等固定秒数。
  - 该横幅同时复用为对局前 VS 预告画面。
- **建连失败**：提示"连接失败，正在重新匹配"，自动回到匹配中状态继续排队（用户可随时 ✕ 取消）。

实现定案（2026-11-17，切片 37）：

- **配对即开局**（偏离本节上文"matched 后双方以房间码走 create/join 等价路径"）：服务器配对时直接开好房间并置为开局段，双方在同一条连接上收 `matched` + `start`——免房间页/准备门，少两轮 ready/begin 往返；房间机器完全共用（hello 收齐仍发第二段 start 开跑）。偏离理由：排队双方连接已在手，重走 join 是纯开销。
- **种子随 matched 携带**：`matched { seed }` 即权威种子（兼作 sim seed，进 configHash），匹配路径无独立 map-roll 消息；matched 固定 `team: true`。
- **VS 横幅头像**暂以位次色块占位（P1 蓝/P2 粉，同选人页色族）——平台头像资料接入归切片 38；横幅构建函数导出复用（对局前预告）。
- **浏览列表快照字段**：`room-list { room, host, team, joinable, started }`——joinable=false 时以 started 区分"已满/已开局"展示。

## 7. 选人与援助（联机版双光标）

机制**复刻原版本地双人**（`SelectFighterStage.initSelecter`：`isVsPeople()` 时 P1/P2 光标同时存在、各自操作、互不阻塞），从"同一台键盘"搬到"两台客户端"：

- **双方同时选人**：各自光标独立移动，能实时看到对方光标悬浮在哪个角色上；
- **允许同角色**（镜像对决合法）；
- **双色框区分**：P1/P2 各一个颜色的框标示双方的光标悬浮与锁定位置（色值实现时参照原版 P2 光标色，不在规格层定死）；
- **选中即锁**：无反悔、无二次确认；双方都锁后自动进入下一阶段（角色 → 援助 → 地图），援助阶段同理；
- **团队模式**：同原版节奏，每光标连续锁定 3 名角色（`selectTimesCount = 3`），再进援助（1 名）；
- 随机角色按钮（原版有）联机版沿用：各自可点，锁定时**此刻解析**成具体角色后按最终项同步（2026-11-17 实现定案；自身重复锁定同角色亦允许）。

**同步设计**（选人页不在确定性 sim 内，是 app 层 UI 状态机，消息驱动）：

- 光标位置：本端光标跟随本端鼠标 hover（与切片 15 起的选人页交互一致；原版键盘驱动不移植——2026-11-17 实现定案），变化频率低，**变更即广播**（轻量消息，新位置覆盖旧位置，无需可靠有序通道）；
- 锁定：沿用既有 `pick` 消息改为**累计快照覆盖式**上行——每次锁定发按锁定次序的全量快照（`fighters[]/assists[]`），对端只留最新（3 秒重发兜底幂等）；角色/援助选满后的地图尾沿用最终 pick（map 仅 P1 携带，P2 选满后收到即移交加载页）；
- 阶段推进由**双方锁定齐套**判定，两端各自本地推导，谁齐套谁切阶段（判定输入一致，结果一致，无需服务器裁决）。

## 8. 地图阶段（援助选完之后）

两种模式，由房间设置（或匹配固定属性）决定：

- **房主选择**（创建房间且未勾选随机地图）：
  - **只有房主能切换地图**；客座无操作权，但**实时看到房主切换**；
  - 房主确认地图 → 双方进对局。
- **开箱抽取**（勾选随机地图，或匹配模式）：
  - CS:GO 开箱式表现：横向地图缩略图长列快速滚动掠过，中央高亮指示框，逐渐减速，定格在抽中的地图上；
  - 时长**约 4 秒**：起步加速 ~0.8s → 高速滚动并开始减速 ~2.2s → 滑入停框 ~0.7s → 定格高亮展示结果 ~0.8s；
  - **不可跳过、不可重抽**；
  - **结果产生**：随机种子由**服务器**在开局时生成并广播（建房与匹配两条路都走服务器，天然有权威点），客户端只负责播动画——两端定格结果天然一致；种子进 `configHash` 参与互验。

实现定案（2026-11-17，切片 36）：

- **种子生成时机 = begin**（`start` 广播后追加 `map-roll { seed }`）：同一颗种子兼作**对局 sim seed**（§9"既有对局 seed 统一服务器权威"一并落地，`configHash.seed` 随之变化；solo/local 恒 seed=1 不受影响）。
- **定格解析**：`maps[|seed| % n]`，两端同一 select 数据，取模即一致；无需额外的随机数生成器。
- **滚动演出**：地图序列重复 3 遍组成长条，行程 = 起步第 1 格居中 → 中段目标实例居中；单段 `easeInOutQuint`（~3.4s）近似规格的分段节奏 + 定格高亮 0.8s，总时长 ~4.2s（偏离登记：分段边界不逐一复刻，总长吻合"约 4 秒"）；地图名随居中项实时更新，定格播确认音。
- **房主选择的实时跟随**：房主每次轮盘切换即发 `map-pick { map }`（随机项广播键 `'random'`，确认时才由房主解析成具体 id 走最终 `pick.map`）；客座渲染同款只读轮盘（无交互），收到即翻页。
- **两端收尾无需握手**：roll 动画时长确定性一致，定格后各自独立进加载页；pick 3s 重发兜底照常（对端在 roll 中收到锁定快照无害）。

## 9. 协议词表扩展（`packages/net/protocol.ts`）

在既有词表（`create/join/welcome/error/hello/pick/start/input/hash/peer-lost`）上扩展。**服务器解析房间语义类，透传 UI 同步类**（与 `input/hash` 同待遇）：

```
房间语义（服务器解析、广播）
  room-config   房主 → 服务器：设置变更 { public?, randomMap?, team? }，服务器广播 room-config
  room-info     服务器 → 房内成员：成员昵称/准备状态/设置快照（入房即发，变更即发）
  ready         客座 → 服务器：准备状态切换 { ready: boolean }
  begin         房主 → 服务器：请求开始；服务器校验客座已准备 → 广播 start
  list-rooms / room-list   浏览列表请求/应答（轮询；快照 { room, host, team, joinable, started }）
  queue / unqueue          加入/退出匹配队列
  matched       服务器 → 双方：匹配成功 { room, player, team, seed, opponent: { name } }，随后直接 start（切片 37 实现定案：配对即开局，见 §6）

UI 同步（透传给对端）
  cursor        选人/援助阶段光标位置 { stage: 'fighter'|'assist', idx, player }
  pick          阶段锁定（沿用既有消息；切片 35 扩展 locked 累计快照 {fighters[], assists[]} 覆盖式上行）
  map-pick      房主切换/确认地图 { map }
  map-roll      开箱种子 { seed }（服务器广播，收到才开始播动画）
```

要点：

- `input/hash/peer-lost` 与对局期语义**零改动**；
- `seed`（开箱地图、以及既有对局 seed）统一由服务器权威生成，进 `configHash`；
- 团队模式 roster 进 `configHash`（切片 35 尾巴）：hello 的 `configHash` 覆盖出场序 roster id 表——两端由同一累计选人 flow 装配，序天然一致，不一致即开局报错而非中途失步；
- 匹配成功后"建连"复用建房/入房的同一套房间机器（不另起一套连接；2026-11-17 切片 37 定案：服务器配对即装配开局段，见 §6 实现定案）。

## 10. 异常流（定案）

| 场景 | 处理 |
|---|---|
| 房间等待期客座掉线 | 房主收到"对方已离开"，房间保留，可继续等待/邀请 |
| 房主在房间页掉线 | 房间解散，客座收到提示回主菜单（2 人房不做房主转移） |
| 选人/地图/对局中掉线 | 提示"连接已断开"，双方回主菜单（lockstep 无重连，既定语义） |
| 匹配成功但建连失败 | "连接失败，正在重新匹配"→ 自动回队列继续匹配 |
| 加入已满/已开局房间 | 明确错误提示（复用 room-full / room-not-found） |

## 11. 与平台的对齐点（待平台侧确认）

1. **身份凭证**：凭证格式、服务器侧验证方式（对应 BeginAuthSession 的接口）、时效；
2. **邀请深链**：邀请发送 API 的形状、进入游戏页时连接参数的传递方式（postMessage 载荷约定）、参数中至少含房间码；
3. **平台昵称/头像**：游戏可获取的资料字段与更新时机（VS 横幅与房间页要用）；
4. **用户 ID 稳定性**：作为服务器侧玩家档案主键的持久性保证。

以上确认前，§2/§4/§6 涉及平台接口处按"结构子集 duck typing"（`platform.ts` 先例）留出接缝实现，不阻塞服务器与 UI 开发。
